# AidFlow — 8 分鐘 Demo 腳本

> 事前：`docker compose up -d` 後執行 `bash client/seed_demo.sh`，先把印出的 URL 開在分頁。
> 建議用電腦開後台、用手機（或無痕視窗）開公開端，現場示範「兩位不同民眾回報」。

## 0. 一句話（15 秒）

> 「AidFlow 不是一個寫死的災情網站，而是一個**災害情境驅動的平台生成器**：描述這次災害，系統就生成一套公開災情網站和政府後台，而且『兩人以上回報同一地點就自動成案』這條治理規則是確定性程式，不靠 AI。」

## 1. 規劃與生成（2 分鐘）

1. `/console/new` 貼上：
   「南投縣仁愛鄉因豪雨造成道路坍方、土石流與積淹水，希望建立全民災情通報與即時處理平台。」
2. 指出分析結果：地區＝南投縣仁愛鄉；災害＝豪雨／土石流／淹水；主要災情；回報者；需要的資料。
3. 指出建議：通報類別只剩與豪雨相關的 11 類（沒有瓦斯外洩）、13 個圖層（含水利署水位、消防署避難所、南投消防單位）、成案規則放寬到 150 公尺／120 分鐘並說明理由、「需金鑰」的圖層誠實標示。
4. 取消勾選一個非核心模組（例如趨勢圖），按「確認並建立平台」。
   - 「AI 只建議，真正生成是 deterministic composer：核心模組與相依模組自動補齊，註冊表以外的 id 會被拒絕。」

## 2. 公開網站（1.5 分鐘）

5. 開啟公開網站（建議先展示 seed 好的南投豪雨平台 `/p/{slug}`，資料較豐富）：
   - 第一眼：KPI（目前災情／待派工／處理中／已完成／高風險）與「通報增加中」。
   - 第二眼：地圖——方塊是正式案件（數字＝回報人數、角標＝狀態），虛線圓是還沒成案的多人回報。
   - 打開圖層面板：切換熱區、只看「政府處理中」、載入水利署水位站（真實 API）。
   - 右側最新災情，下方趨勢與官方警戒（未設 CWA 金鑰時會說明「暫無資料」，不是假資料）。

## 3. 兩人成案（2 分鐘，主秀）

6. 手機開 `/p/{slug}/report`：選「道路坍方」→ GPS 或地圖點選 → 拍照 → 選「村里長」→ 送出。
   - 回應：「目前 1 位回報者，再 1 位不同回報者確認即自動成案」。
7. 同一支手機再送一次同地點 → 仍然是 1 位（同一人重複不計）。
8. 另一台裝置／無痕視窗在 100 公尺內送「道路中斷」（相近類別）→ 回應「已自動成案（NT-…），進入政府待派工」。

## 4. 政府派工與公開透明（2 分鐘）

9. 指揮中心 `/console/platforms/{id}`：案件佇列最上面出現「待派工」；點「派工」。
10. 案件工作台：輸入處理單位「公路局中區養護工程分局埔里工務段」→「確認成案並派遣」。
11. 回到手機的案件頁：狀態已是「已派員」，時間軸多了一筆。
12. 後台依序按「人員出發 → 人員抵達 → 開始處理」，中間新增一則公開進度「單線通行預計 2 小時後恢復」，最後「處理完成」。
13. 手機案件頁：進度條走到「已完成」，時間軸完整列出第一筆通報 → 第二筆 → 達到門檻 → 成案 → 派員 → 抵達 → 處理 → 完成，全部來自真實事件。
14. 後台「稽核軌跡」分頁：每一步都有 outbox 事件。

## 5. 收尾（30 秒）

- 公開端看不到姓名、電話、門牌；後台看得到（因為要聯繫）。
- 換一段地震描述再 plan 一次：類別變成建築損害／瓦斯外洩，圖層換成建物與消防單位——同一套註冊表，不同災害，不同平台。
